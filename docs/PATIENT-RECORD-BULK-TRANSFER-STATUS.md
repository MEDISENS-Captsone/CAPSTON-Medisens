# Admin Patient Record Bulk Transfer

## Implemented locally

The Admin Import / Export / History UI uses the existing `medisens-secure-records` Edge Function crypto contract. The Admin transfer Edge Function repeats signed-user and active-Admin checks, then proxies import/export to the secure-records function, which repeats those checks before using its server-only service client.

Imports and exports use explicit profile and clinical field projections. Sensitive fields are encrypted/decrypted with the existing AES-256-GCM service, per-table `crypto_ref` AAD, and patient blind-index helper. Workbooks do not include ciphertext, `crypto_ref`, key versions, encryption timestamps, or blind indexes. Private URLs, signatures, consent records, and attachments are excluded. New patients remain `consent_signed=false`; import does not create consent.

Same-system patient refs are persisted by the server as `MEDISENS-PATIENT-<id>` (or reuse an existing mapping). Clinical refs use `<table>:<source-id>`, and export registers those source mappings against the original records before generating the workbook. This prevents exporting and re-importing into the same database from duplicating mapped patients or clinical rows. Destination IDs are generated by MediSens. Database import checks each reference’s source patient and record type, and verifies its destination foreign key points to that patient.

Profile UPDATE rows require an explicit non-empty `update_fields` list. The secure Edge Function decrypts and merges the existing sensitive profile before re-encrypting it; SQL only changes listed fields and preserves the existing crypto ref. Clinical rows are insert-only and retry-safe through source mappings.

For status history, lab requests are created Pending, then a Completed result follows the existing result validation and request-sync triggers. A source Completed request without its Completed result is rejected. Prescriptions are created Pending, then a Dispensed record follows the existing guarded status transition with its original `dispensed_at`. Completed consultations retain `status` and `completed_at`. No trigger is disabled or bypassed.

The secure Edge Function generates XLSX and CSV files server-side and returns them only through the authenticated function response. XLSX includes separate relational worksheets; CSV exports profiles only. Server limits are 100 patients, 5,000 records and 10 MiB transfer data. Export operation counts are derived server-side; requested, generated, failed, and client-reported download initiation are separate history states. A client download click is not proof that the user saved or opened the file. No clinical narratives are written to audit metadata.

## Authorization and provenance limits

Only active Admin accounts may call bulk transfer operations. Transfer tables have RLS enabled with no authenticated-client grants; SECURITY DEFINER routines use a blank search path and are executable only by `service_role`. Browser role values are ignored. The service-role key remains in Edge Function secrets.

The source schema stores several author values (`attending_provider`, `requested_by`, `performed_by`, `doctor_name`) as free text, without a staff-profile foreign key or signed workbook provenance. The transfer preserves those source-reported values and records the importing Admin separately in transfer mappings/history; it does not create or impersonate a staff account. Those text values cannot be independently verified as authentic authorship. A signing/trust contract is still needed before describing imported author attribution as verified.
